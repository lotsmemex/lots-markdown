# Open-speed measurements, 2026-11-20

Machine: MacBook Pro M1 Pro, 16 GB, macOS 27. Heavily loaded during every run (load average 90–280), so absolute numbers are upper bounds; the empty AppKit window (`bench/floor.swift`) is measured in the same runs as a reference. Corpus: `bench/gen_corpus.py` (mixed Chinese/English, headings, lists, tables, code). Renderer: the temporary `apps/render-stub` (pulldown-cmark 0.13). Medians.

## macOS app (`bench/macos_open.py`, 15 runs, load 280)

| File | Process start → first frame | File read → first frame | Markdown → HTML | Start → preview ready |
| --- | --- | --- | --- | --- |
| empty AppKit window | 225 ms | – | – | – |
| 100 KB | 308 ms | 107 ms | 1 ms | 734 ms |
| 1 MB | 407–538 ms | 120 ms | 12 ms | 1.1–1.3 s |
| 10 MB | 342–374 ms | 131–136 ms | 112–126 ms | 2.5 s |
| 100 MB (single run) | 1.04 s | 712 ms | 34 ms (2 MB prefix) | 2.2 s, 481 MB peak RSS |

Files above 16 MB preview only their first 2 MB (cut at a blank line outside fenced code). Before that change the 100 MB preview never finished (WebContent at 100% CPU for over 6 minutes).

The Android bottleneck is the source `TextView` laying out the whole file, not rendering. Next step there: show the rendered view first and load the source view lazily or in chunks.
